# Illux Image Tool v0.2 — Size-based resampling, bicubic, macOS — Design

Date: 2026-11-04
Status: Draft for approval
Builds on: `2026-10-23-illux-image-tool-design.md` (v0.1, released as v0.1.0) and
`docs/superpowers/decisions/2026-10-23-build-decisions.md` (rulings R1–R47 still
apply unless changed here).

## 1. Intent

Requested by Illux:

1. Scaling, up **and** down, uses **bicubic interpolation**.
2. The target resolution depends on the image's **print size**. Illux's spec:
   - images over 40 × 30 cm: scale up/down to **200 ppi**
   - images under 40 × 30 cm: scale up/down to **300 ppi**
   An image whose ppi is already close to its target (inside an acceptable
   range) is left alone. All of this must be adjustable in the program,
   "thought through properly" (e.g. measuring by longest side), and saved.
3. The program also runs on **macOS**, downloaded manually (no App Store), and
   updates the same way as on Windows.

Context from Illux: production use with Esko Automation Engine stays on a
**dedicated Windows server/PC** running 24/7 that no people use. The Macs are for
**testing and possibly later use with watched folders** — not for AE. Test Macs:
Mac mini 2024 (Apple M4, macOS 15.3.1) and Mac Studio 2022 (Apple M1 Max,
macOS 26.6.2).

## 2. Goals

- Bicubic resampling in both directions.
- Downscaling is now allowed (replaces v0.1's non-goal "no downsampling").
- Size rules (§5) set in the settings window, saved, and used by the AE
  command-line runs and all watched folders.
- A macOS build (Apple silicon, macOS 15+) with the same image processing,
  watched folders, settings window, update popup and click-to-update.
- Windows keeps working as before apart from these changes; existing v0.1.0
  installs update to v0.2.0 with "Update now".

## 3. Non-goals

- No Esko AE scripts or AE support on macOS.
- No App Store, no Apple code signing/notarisation (no Apple Developer account).
- No Intel Macs, no macOS older than 15.
- No per-folder or per-AE-step size rules (one shared setting).
- No special handling of 1-bit line art: it is resampled like everything else
  and becomes grayscale (ruling R18) — Illux: "skal skaleres også, vi kan ændre
  senere".

## 4. Anti-goals

- Any change in image fidelity behaviour other than the requested ones (colour,
  ICC, metadata, orientation, "no unnecessary JPEG re-encode" rules stay).
- Weakening the v0.1 security model on Windows.
- A Mac build that only "sort of" works: it must pass an automated
  install/update/uninstall smoke test on GitHub's macOS runners.

## 5. Size-based resampling (both platforms)

### 5.1 Concepts

- **Print size** = pixels ÷ ppi, per axis, in cm (the image's current physical
  size; it is kept when resampling). If the file stores no resolution, the
  existing `missingppi` policy decides (default: assume 72 ppi, Warning).
- A **size rule** has: a name, a **size test**, a **target ppi**, and an
  **"leave alone" range** (min ppi, max ppi) around the target.
- Rules are checked **top to bottom**; the first rule whose size test matches
  is used. The **last rule always matches** ("all other images").

### 5.2 Size tests (selectable per rule)

| Test | Matches when… |
|---|---|
| Fits within W × H cm | the image fits inside W × H in either orientation (short side ≤ H and long side ≤ W, with W ≥ H) |
| Longest side ≤ X cm | the image's longest side is at most X |
| Shortest side ≤ X cm | the image's shortest side is at most X |
| Area ≤ X cm² | width × height is at most X |
| All other images | always (only for the last rule) |

### 5.3 Defaults (Illux's spec)

1. **Small** — Fits within **40 × 30 cm** → target **300 ppi**, leave alone if
   ppi is **250–350**.
2. **Large** — All other images → target **200 ppi**, leave alone if ppi is
   **150–250**.

Examples: 38 × 28 cm → small → 300 ppi. 60 × 20 cm → large → 200 ppi (too long
for 40 × 30). 35 × 35 cm → large (too wide for 30). "Fits within, either
orientation" is my call as the most direct reading of "under 40 × 30 cm"
(Illux: "whatever makes most sense"); it can be changed in Settings.

### 5.4 Rule applied to an image

1. Compute print size from the current ppi (per axis).
2. Pick the first matching rule.
3. Per axis (keeps ruling R13's per-axis handling): if ppi < min or ppi > max,
   resample that axis to the target; otherwise leave that axis unchanged.
4. Physical size is kept. Existing guards stay: >4× enlargement → Warning;
   >65,000 px → Error.
5. The AE log line names the rule, e.g.
   `300→200 ppi (rule "Large": 62.3 × 41.5 cm; 7360×4912 → 4907×3275, bicubic)`.

### 5.5 Settings window

A "Resolution rules" section: a table of rules (name, size test + its numbers,
target ppi, leave-alone min/max), with Add / Edit / Remove / Move up / Move down,
and "Reset to Illux defaults". Validation (refuse with a short message):
whole numbers; 1 ≤ min ≤ target ≤ max ≤ 2400; sizes 0.1–1000 cm; exactly one
"All other images" rule, which is last. Saved in `config.json` (admin-only on
Windows, per R34):

```json
"resolutionRules": [
  { "name": "Small", "test": "fitsWithin", "widthCm": 40, "heightCm": 30,
    "targetPpi": 300, "minPpi": 250, "maxPpi": 350 },
  { "name": "Large", "test": "all",
    "targetPpi": 200, "minPpi": 150, "maxPpi": 250 }
]
```

Missing section → the defaults above. Invalid section → the service keeps the
last good rules, the CLI uses the defaults, both with a Warning in the
log/AE output. The CLI reads `config.json` on every run, so changes apply
without restarting anything.

### 5.6 Filter

- Default filter: **Bicubic** (Photoshop's plain "Bicubic" = Keys cubic with
  a = −0.5 = ImageMagick `Catrom`), for up- and downscaling. Illux didn't name a
  Photoshop variant ("Bicubic Smoother/Sharper/Automatic"); plain Bicubic is my
  call and easy to change later.
- `filter=` AE parameter stays (`bicubic` default; `lanczos`, `mitchell` still
  accepted).

### 5.7 AE parameters and existing configs

- The operation is renamed **`resample`**; `upsample` stays accepted as an alias.
- `resample=N` / `upsample=N` in an **AE ticket** → Error: "ppi is set in
  Illux Image Tool Settings (Resolution rules), not in the AE ticket".
- No migration of existing watched folders or AE tickets: Illux has not set up
  any folders or AE steps yet (Illux: "we choose the folders ourselves"). The
  program never creates or changes watched folders on its own.
- Help text, `docs/ae-setup.md` and README updated.

## 6. macOS

### 6.1 What the Mac gets

Same core processing, watched folders running in the background without anyone
logged in, settings window + menu-bar icon with the update popup, and
click-to-update. Apple silicon (arm64) only, macOS 15 or later.

### 6.2 Distribution

- **`IlluxImageTool-X.Y.Z-macOS-arm64.pkg`** + `.sha256`, attached to the same
  GitHub release as the Windows `IlluxImageTool-Setup-X.Y.Z.exe`. `.pkg`
  rather than `.dmg` because it must install a background service (Illux: "a
  dmg or something else").
- Unsigned: first install needs **System Settings → Privacy & Security → Open
  Anyway**; README explains it in two lines. Updates run through the
  command-line installer as root and are not blocked by Gatekeeper.

### 6.3 Background service

- launchd **LaunchDaemon** `dk.illux.imagetool.watcher`, running as root,
  started at boot, restarted if it stops.
- Data folder `/Library/Application Support/Illux Image Tool/` owned by root;
  `config.json` writable by the `admin` group, readable by all; `update/` and
  service logs root-only. Same rule as Windows: no root file operations in
  user-writable folders.
- Watched folders on the Mac: **local folders** outside the user's protected
  folders (e.g. `/Users/Shared/...`) are supported. Desktop/Documents/Downloads,
  external drives and network shares need macOS "Full Disk Access" or a
  logged-in user and are **not supported in v0.2** (documented). My call —
  Illux didn't say where the Mac folders will live; it's testing, and this can
  be extended later.
- Signals from the menu-bar app to the daemon ("Check for updates", "Update
  now") use a mechanism owned by the daemon (e.g. a Unix socket it creates) —
  never files in a user-writable folder (ruling R37's intent).

### 6.4 Settings window and tray on both platforms

- Rebuilt with a cross-platform UI toolkit (my call: **Avalonia**), replacing
  Windows Forms, so one UI serves both. Windows rules stay (window self-elevates
  per R34; tray stays non-elevated). The Windows installer should stay under
  ~100 MB; if Avalonia pushes it over, the builder reports back before going on.
- On macOS, admin actions (start/stop the service) use the standard macOS
  administrator prompt; no "change service account" on macOS.

### 6.5 Updates

- The updater picks its platform's asset (`.exe` on Windows,
  `macOS-arm64.pkg` on Mac) with the same SHA-256 check, host allow-list,
  size cap and idle-wait.
- macOS: the daemon installs with `/usr/sbin/installer -pkg … -target /`.
- The release workflow builds Windows on a Windows runner and the Mac package on
  a macOS (Apple silicon) runner; a release always contains both.

### 6.6 Native pieces for macOS

- ImageMagick: a Magick.NET package with macOS arm64 natives next to Windows
  x64; pinned, no open advisories.
- jpegtran: built from the official libjpeg-turbo 3.2.0 source (hash verified)
  on the macOS runner; Windows keeps the official binary.
- Windows-only code (ACLs, Windows service, named events, VC++ runtime, Inno
  Setup) stays Windows-only; the Mac gets equivalents behind the same Core
  interfaces.

## 7. Acceptance checks

- Size rules: tests for each size test, rule order, first-match, last rule
  always matches, per-axis leave-alone/resample to target, physical size kept,
  bicubic used, the examples in §5.3, settings round-trip, invalid settings
  rejected, CLI picks up a changed rule without restart, AE `=N` Error.
- Windows: existing CI smoke test still green; v0.1.0 → v0.2.0 upgrade keeps
  config.json and adds the default rules; installer size reported.
- macOS (GitHub Apple-silicon runner): install the pkg, daemon running, a
  watched folder converts a file, settings saved, upgrade to a newer build keeps
  config, uninstall removes the daemon.
- Manual (Illux): install the pkg on one test Mac, set up a watched folder under
  `/Users/Shared`; compare a downscaled and an upscaled image with Photoshop.

## 8. Left to the builder

- Exact macOS IPC mechanism and uninstall method (an uninstall script shipped
  in the app folder is fine).
- How the Mac pkg is built (pkgbuild/productbuild) in CI.
