# PDF input decisions (2026-11-05)

Rulings taken while building PDF input, in order. Same format as the earlier ledgers: what was decided, why, and what it costs if wrong. R1-R47 ([2026-10-23-build-decisions.md](2026-10-23-build-decisions.md)) and V1-V15 ([2026-11-04-v0.2-decisions.md](2026-11-04-v0.2-decisions.md)) still apply.

## Spike (Task 1)

Throwaway console code (not committed) ran a reader and three writers against every `TestPdfs` file (one JPEG, 16-bit PNG with alpha, rotated 90° and 30°, two pages, image in a form with `/Matrix`, one image on two pages, inline image, no images, encrypted, PDF 1.5 object stream + xref stream, Chili-like) and against the five real CHILI Publish samples from Illux (read in place, outputs only in a temp folder, nothing from them in the repo). PdfPig **0.1.16** throughout: newest stable on nuget.org and GitHub (v0.1.16, 2026-08-22; later builds are only `0.1.17-alpha-*`), Apache 2.0, managed only, so it runs unchanged on Windows x64 and macOS arm64.

### Chili PDF shape

All five samples share one structure (only sizes differ):

- `%PDF-1.6`, CR (`\r`) line endings, one classic xref table and trailer (`/Root /Info /Size /ID`), no object streams, no xref stream, no incremental updates, not encrypted. 11 objects (`/Size 12`). Info `/Producer (CHILI Publish)`; catalog has an XMP `/Metadata` stream. No output intent.
- One page. `/UserUnit 1`; MediaBox = TrimBox = BleedBox; no `/Rotate`. Resources: one form XObject and one ExtGState (`/BM /Normal /OPM 1`).
- Page content: `q /GS1 gs q sx 0 0 sy 0 0 cm /Frm… Do Q Q` with sx, sy slightly above 1 (1.00135 / 1.00202 or swapped, 1.00402 / 1.00627).
- The form XObject: no `/Matrix`, `/Resources` by indirect reference, Flate content, `/BBox [0 0 w h]`. Its content flips the y axis (`1 0 0 -1 0 h cm`), may shift (`1 0 0 1 dx dy cm`), clips to a rectangle (`re`-style path, `W n`) and draws the image with `w 0 0 -h' 0 h' cm /Img1 Do` (negative height: row 0 at the top).
- The image: `/DCTDecode`, 8 bit, `/ColorSpace [/ICCBased n 0 R]` (3-component profile, Flate), empty `/DecodeParms << >>`, no mask. 2086 × 1353 to 8192 × 5464 px; files 1.4 to 66.6 MB.
- The drawn image is not always the page: in one sample it is 0.7 pt narrower than the page and shifted 3.55 pt; in another it is taller than the page and the form's clip cuts it. The drawn size is still the full image axes (constraints), not the clip.

`TestPdfs.ChiliLike` builds this shape (with LF line endings and 4-decimal scale factors).

Drawn size and ppi read from the five samples (reader below; both axes; matches PdfPig's own image corners to 4 decimals):

## Rulings

- **P1 (writer): option (b), PdfPig read + our own full rewrite.** Every object of the input is re-serialised with PdfPig's `TokenWriter`, the replaced image streams are written in their place, and a classic xref table and trailer are written by our code.
  - *How (for Task 5's `PdfRewriter.Write`):* open with `PdfDocument.Open`; for each `IndirectReference` in `document.Structure.CrossReferenceTable.ObjectOffsets.Keys` (ascending) get `document.Structure.GetObject(reference)` (an `ObjectToken`); skip streams whose `/Type` is `/ObjStm` or `/XRef`; for a replaced id use `new StreamToken(dictionary, data)`; write with `TokenWriter.Instance.WriteToken(new ObjectToken(XrefLocation.File(0), reference, token), output)` and record the offset. Header: the input's own `%PDF-x.y` line (read from the file, never lowered) plus a binary comment line. Trailer: `/Size` (highest number + 1), `/Root`, `/Info` and `/ID` copied from `document.Structure.Trailer` (`Root`, `Info`, `Identifier`); never `/Prev`, `/XRefStm` or `/Encrypt`. `PdfImageStream.Dictionary` bytes are parsed with `new CoreTokenScanner(new MemoryInputBytes(bytes), true, new StackDepthGuard(64))` into a `DictionaryToken` (must be exactly one dictionary), any `/Length` dropped and a direct `/Length` = data length set.
  - *Evidence:* on all 12 test files and all 5 Chili samples, replacing the image with a 120 × 90 JPEG (new size, new dictionary) reopened in PdfPig with the same page count, MediaBox, page dictionary, form and every other object equal token for token (stream data byte for byte), and the reader found the new image at the old drawn size. The xref-stream file came out as a clean classic file, header still 1.5 (classic tables are valid in every version). A hand-made object with tricky strings (`\351`, `\000`, escaped parentheses, PDFDocEncoding bytes `\200..\240`, a UTF-16 literal with BOM, hex strings, `#20` in a name) came back byte-identical in its strings; only whitespace and number spelling change (`-.5` → `-0.5`, `3.` → `3`), which is the same value. Old image data is gone: a sample with its 1.48 MB image replaced by 6.6 kB came out at 10.4 kB. Timing on the 66.6 MB sample, replacing the 69.8 MB image with the same amount of data: 0.45 s end to end (0.23 s of it start-up and open), peak working set 320 MB, output 69.8 MB.
  - *Why not the others:* (c) incremental update also worked (classic xref section with `/Prev` for classic files, an xref stream section for xref-stream files) but keeps the old image data, so the 66.6 MB sample became 139.6 MB. (a) QPDF, from its official documentation only (nothing downloaded or run here): Apache 2.0; v12.4.2 (2026-09-27) ships official `qpdf-12.4.2-msvc64.zip` (Windows x64) and `qpdf-12.4.2-bin-macos-arm64.zip` assets on GitHub, and builds from source with CMake; `--update-from-json` (JSON v2) replaces a stream with `"dict"` (always the full dictionary; `/Length` ignored) and `"data"` (base64) or `"datafile"`. It works in principle but adds a second, native dependency to bundle and sign on both platforms, a JSON adapter (names, `u:`/`b:` strings, references), and its defaults re-encode LZW/ASCII streams (`--stream-data=compress`, `--decode-level=generalized`; `--stream-data=preserve` turns that off) and generate a new `/ID` with a random element (`--deterministic-id` makes it repeatable). Preference order (b), (a), (c) from the plan, and (b) works.
  - *Notes for Task 5:* (1) build a proper free list (entry 0 links to the first free number, each free entry to the next; the spike wrote unlinked free entries); (2) write a direct `/Length` for every stream, not only replaced ones, so a wrong indirect length that PdfPig repaired on reading is not copied; (3) drop a linearization dictionary (`/Linearized`) if one is present, since its offsets would be wrong; (4) the spike held the file and every stream in memory (peak working set about 4.6 × the file); fine for these sizes; (5) objects only reachable through the dropped object/xref streams do not exist, so nothing is lost there.
  - *Cost if wrong:* a re-serialised file some RIP or preflight rejects although PdfPig reads it. It was only checked with PdfPig here; no independent checker is installed on this PC (HARD RULE). Fallback: (c), which leaves every original byte in place and appends the new objects (the spike's code path is about 40 lines on top of the same token writing), at the price of bigger files; then (a). Verify early with a real RIP/AE run on the Chili samples.
  - *Correction (Task 5):* the evidence above is wrong on two counts. PdfPig 0.1.16's `TokenWriter` changes values: integers beyond 32 bits become `2147483647` (and `-2147483649` is written as nothing), a literal string with PDFDocEncoding bytes such as `\200` is rewritten as UTF-16 (different bytes), and `#` in a name is not escaped. "Strings came back byte-identical" did not hold when re-checked. The comparison through PdfPig also could not show losses that happen while PdfPig reads (P1b).

- **P1a (Task 5, superseded by P1b): our own serializer instead of `TokenWriter`.** `PdfSyntax` writes the tokens: strings from their bytes (`StringToken.GetBytes()` and `HexToken.Bytes` were exact for 5,034 test strings), integers in full, reals without exponent, names `#`-escaped. *Why it was not enough (review):* the losses also happen while PdfPig reads. Names are decoded as UTF-8 or Windows-1252 (`/A#80` reads as "A€"), so a non-ASCII resource key written back no longer matches its use in the untouched content stream. A raw CR or CR LF inside a literal string means LF to a conforming reader, but PdfPig gives 0D. Integers beyond 2^53 are not exact. A writer cannot recover any of these.

- **P1b (controller ruling, binding; Task 5): copy plainly stored objects byte for byte; write again only what must be, and only when exact.**
  - *How:* PdfPig still reads the cross-reference data and every object. An unchanged object stored plainly in the input (`XrefEntryType.File`) is copied raw, from `n g obj` through `endobj`. `PdfRawObjects` finds the range by reading the syntax: `n g obj` must be at the reported offset, strings, hex strings, comments and names are stepped over, and a stream ends at data start + its resolved `/Length` (which must equal the length of PdfPig's data), followed by `endstream` and `endobj` with whitespace or EOL variants. Anything not where expected fails with `InvalidDataException`; nothing is guessed. A copied stream keeps an indirect `/Length`, since its length object is copied too. Only replaced images and objects from object streams are serialised (`PdfSyntax`), and a serialised stream gets a direct `/Length`. `/ObjStm`, `/XRef` and `/Linearized` objects are still dropped, and their numbers become free entries for generation g+1. The classic xref (with a linked free list) and the trailer (`/Size /Root /Info /ID`) are new. The output goes to a `.tmp` file next to the target and is moved into place on success, so an older file there is kept on failure.
  - *Refusal list (`PdfSyntax`, `NotSupportedException`, mapped by Task 6 to `the PDF could not be read (<reason>)`):* a name with any non-ASCII character; a literal string containing 0x0D; a whole number outside the 32-bit integer range (covers ≥ 2^53, and whole-number reals PdfPig reports as integers); a non-finite number; a real whose plain-decimal form does not parse back to the same value; a token that is not a PDF object. The rewriter prefixes `object n g R cannot be written back exactly (…)` or `the trailer cannot be written back exactly (…)`. Replacement dictionaries that cannot be written exactly are the caller's fault (`ArgumentException`); `PdfImageEncoder` already refuses them with `NotSupportedException`.
  - *Evidence:* with no replacements, all five Chili samples come out with every object (11 of 11) byte-identical to the input; with one replaced image, the other 10 are. Only the header's line end, the separators between objects, the xref and the trailer differ. The 66.6 MB sample takes 0.26 s with peak working set 121 MB; replacing its 69.8 MB image with the same amount of data takes 0.43–0.48 s, peak 122 MB.
  - *Cost if wrong:* a PDF with a non-ASCII name, or a CR in a string, inside an object stream goes to Error although it is fine. None of the Chili samples has object streams.

- **P2 (reader): our own content-stream walk over PdfPig's parsed operations**, not PdfPig's `IPdfImage.BoundingBox`.
  - *How (for Task 2's `PdfImageScanner.Scan(path)`):* for page *n*, `page.Operations` (already parsed, all content streams concatenated) is walked with a CTM starting at identity and a stack: `Push` (`q`) pushes, `Pop` (`Q`) pops, `ModifyCurrentTransformationMatrix` (`cm`) sets CTM = `TransformationMatrix.FromArray(op.Value).Multiply(CTM)`, `BeginInlineImage` (`BI`) counts an inline image, `InvokeNamedXObject` (`Do`) looks `op.Name` up in the current resources' `/XObject` dictionary. The entry is an `IndirectReferenceToken` whose `.Data` is the image's `IndirectReference` (the id). `document.Structure.GetObject(reference).Data` is the `StreamToken`; `/Subtype /Image` → record (reference, CTM); `/Subtype /Form` → CTM' = `/Matrix` (identity if absent) `.Multiply(CTM)`, resources = the form's `/Resources` or the caller's, content = `stream.Decode(document.Structure.FilterProvider, document.Structure.TokenScanner)` parsed with `new PageContentParser(ReflectionGraphicsStateOperationFactory.Instance, new StackDepthGuard(n), true).Parse(pageNumber, new MemoryInputBytes(bytes), log)` (an `ILog` that drops messages), then walk recursively. Page resources: `/Resources` from the page dictionary or, if absent, up the `/Parent` chain. `/Resources` and the `/XObject` sub-dictionary may be indirect references (Chili's form does this): dereference both. Drawn lengths: width axis = √(a² + b²), height axis = √(c² + d²) of the CTM, times the page's `/UserUnit` (default 1), in points (÷ 72 × 2.54 for cm).
  - *Evidence:* on every test file the walk gave the right reference, all six matrix values and the right axis lengths: 90° and 30° turns (10 × 7.5 cm kept), the form with `/Matrix [2 0 0 1 0 0]` plus nested `cm`, the reused image twice (same reference, 10 × 7.5 and 20 × 15 cm), the inline image counted, the xref-stream file. On the Chili samples it followed page `cm` → form → flip → clip → image `cm` and agreed with PdfPig's corners (table above).
  - *Why not `BoundingBox`:* `Page.GetImages()` gives corners but no object reference (`XObjectImage` has none), so a reused image or an image's soft mask cannot be tied to its object; `Bounds` is already obsolete; corner naming differs for inline images. A subclass of PdfPig's `BaseStreamProcessor` with a custom page factory would expose `ResourceStore.TryGetXObjectReference` and the CTM, but means implementing its 20 abstract members (glyphs, paths, clipping, shading, marked content) of an advanced API; the walk is about 80 lines on stable types.
  - *Notes for Tasks 2/3:* guard form recursion (depth limit and a visited set of form references, as a form can invoke itself); a `Do` of a name missing from the resources needs a decision (Task 2's call). `PdfDocument.Open` throws `PdfDocumentEncryptedException` for the `Encrypted` test file; a real file encrypted with an empty user password opens with `IsEncrypted == true`, so check both for `encrypted PDFs are not supported`.
  - *Cost if wrong:* wrong drawn sizes mean wrong ppi decisions. The walk ignores text-render and Type 3 glyph images (not expected in Chili PDFs). Fallback: cross-check against PdfPig's `BoundingBox` per page (same count, same lengths) and fail the PDF on a mismatch.

- **P4 (known gaps of the reader).** The P2 walk finds images drawn by `Do` in page content and in forms reached from it. Not found, and so never processed: images drawn only from annotation appearance streams, from tiling patterns or from soft-mask groups; images drawn through text render modes; Type 3 font glyph images. Inline images are counted (`N inline image(s) not processed`) but not processed. A `Do` of a name missing from the resources is ignored. Cost: such an image stays at its original size. None of this occurs in the Chili samples.

- **P3: PdfPig 0.1.16 is pinned** for Core as well (it is already the test project's version). Cost: none; updates are deliberate.
